## The grant

At sign-in, auth-service issues a refresh token. The SDK stores it as the user's **grant**, keyed by the user's `sub` (the *grant id*). It is the only long-lived credential your backend holds for that user, so a `GrantStore` implementation should encrypt it at rest.

auth-service **rotates** the refresh token on every use: each refresh returns a new one that replaces the previous, and replaying a stale token revokes the whole family. A store therefore holds exactly one value per grant, and two refreshes of the same grant must never run at the same time.

## GrantManager

`GrantManager` is the only place that refreshes tokens. It:

- serialises the refreshes of one grant through a `GrantLock` (tasks of other grants run in parallel);
- persists the rotated refresh token in the `GrantStore` after each refresh, and keeps the stored one when the provider does not rotate;
- mints **access tokens per resource** and caches them in memory until `expiry_skew_seconds` (30 by default) before they expire. Access tokens are never persisted;
- drops the grant and fails with `TOK_002` when the user has no grant or the provider answers `invalid_grant`. Only a new sign-in restores it. Other failures (network, server errors) keep the grant;
- runs each refresh and each revocation to completion on its own Tokio task: a caller that gives up (a dropped request, a timeout) cannot leave the provider with a rotated token that this process never stored.

```rust
use auth_ai::{
    AccessToken, AuthAiError, AuthClient, AuthClientConfig, GrantManager, MemoryGrantStore,
};

fn grant_manager() -> Result<GrantManager, AuthAiError> {
    let auth = AuthClient::new(
        AuthClientConfig::builder(
            "https://auth.example.com",
            "my-app",
            "https://app.example.com/auth/callback",
        )
        .client_secret("<client-secret>")
        .resources(["https://api.example.com"])
        .build()?,
    )?;
    Ok(GrantManager::new(auth, MemoryGrantStore::new()))
}

async fn api_token(grants: &GrantManager, sub: &str) -> Result<AccessToken, AuthAiError> {
    // An access token for one audience (RFC 8707), valid for the resource only.
    grants
        .get_access_token(sub, Some("https://api.example.com"))
        .await
}
```

The returned `AccessToken` has an `access_token` (a `SecretString`: read it with `expose_secret()`) and an `expires_at` in Unix seconds.

## Per-audience tokens

The sign-in asks for every audience in `resources` at once; the code exchange sends no `resource`, so the first token is valid for all of them. Each later refresh then **narrows** the new access token to the single `resource` you ask for. One refresh token, many narrow tokens: a token leaked from the gateway call cannot be replayed against your API.

| Audience | Used for | Minted by |
| --- | --- | --- |
| Your API URL (an entry of `resources`) | Bearer-protected routes of your own API | `grants.get_access_token(sub, Some(resource))` |
| auth-service (`issuer`) | The user's wallet | `ai.for_user(sub)?.wallet` |
| The gateway (`gateway_url`) | LLM and MCP calls | `ai.for_user(sub)?.gateway()?` |

With `gateway_url` set, the configuration adds the gateway URL and the `issuer` to `resources` and the `wallet:self:read` scope to `scopes` automatically. With `resource_sharing(true)`, it adds the `issuer` to `resources` and `resources:self:manage` to `scopes`.

::callout{icon="i-lucide-triangle-alert" color="warning"}
The SDK never sends `scope` on a refresh. The rotated refresh token would be left with the scopes of that request only, permanently stripping `offline_access` and the other scopes from the grant.
::

## Renewing claims

`grants.refresh_tokens(grant_id)` refreshes **without** narrowing to a resource and returns the whole `TokenSet`, ID token included. The sign-in handlers use it to renew a session's claims on a schedule (`claims_renew_seconds`). Failures are those of `get_access_token`.

## Handling a refused token

If an API answers `401` to an access token, call `grants.invalidate(grant_id, Some(resource))` so the next `get_access_token` mints a fresh one. `invalidate` is synchronous. The SDK's own clients (`WalletClient`, `GatewayClient`, the machine API) already do this.

## Several replicas

The default lock, `InProcessGrantLock`, only serialises refreshes inside one process, and the access-token cache is per process too. With several replicas, pass a distributed `GrantLock` (or a row lock in your database) through `GrantManager::builder(auth, store).lock(lock).build()` so two replicas never rotate the same grant at once. See [Implement the stores](/docs/guides/backend/custom-stores).

## Revoking

`grants.revoke(grant_id)` revokes the refresh token at the provider, then forgets the grant even if the provider is unreachable: an outage must not keep the user signed in locally. The provider's refusal is still returned, after the grant was forgotten.
