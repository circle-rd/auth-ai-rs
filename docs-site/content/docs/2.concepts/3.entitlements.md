---
title: Entitlements
description: Roles, permissions, plan features and organisation from the user's claims, and the helpers that read them on the server.
---

auth-service puts the user's entitlements for **your application** into the ID token (and into JWT access tokens). A claim is present only when its scope was granted, which is why the SDK requests `roles`, `permissions` and `features` by default.

| Claim | Rust type | Scope | Meaning |
| --- | --- | --- | --- |
| `roles` | `Option<Vec<String>>` | `roles` | Roles the user holds in your application. |
| `permissions` | `Option<Vec<String>>` | `permissions` | `resource` for read access, `resource.write` for write access. |
| `features` | `Option<BTreeMap<String, FeatureValue>>` | `features` | Feature flags and limits of the user's plan. `FeatureValue` is `Bool`, `Int`, `Float` or `Text`. |
| `plan` | `Option<String>` | — | The user's plan, when present. |
| `org_id` | `Option<String>` | `org` | The organisation, when the scope is granted. |

The claims model is documented in auth-service: [OIDC claims](https://docs.circle-cyber.com/auth-service/docs/concepts/oidc-claims) and [Roles and permissions (RBAC)](https://docs.circle-cyber.com/auth-service/docs/concepts/rbac). The `org` scope is not in the SDK's default `scopes`: add it to `scopes` if you need `org_id`.

## Helpers

Four pure functions read these claims. They accept anything that implements the `EntitlementClaims` trait: `IdTokenClaims`, `AccessTokenClaims` and `UserInfoClaims`.

```rust
use auth_ai::{IdTokenClaims, PermissionAction, get_feature, has_feature, has_permission, has_role};
use serde_json::{Value, json};

fn describe(claims: &IdTokenClaims) -> Value {
    json!({
        "admin": has_role(claims, "admin"),
        "can_write_reports": has_permission(claims, "reports", PermissionAction::Write),
        "can_read_reports": has_permission(claims, "reports", PermissionAction::Read),
        "beta": has_feature(claims, "beta"),
        "seats": get_feature(claims, "seats"),
    })
}
```

- `has_role(claims, role)` is true when `roles` includes `role`.
- `has_permission(claims, resource, action)` checks `resource.write` first: **write implies read**, because auth-service keeps only the highest action. Read access is `resource` alone. `action` is `PermissionAction::Read` or `PermissionAction::Write`.
- `has_feature(claims, key)` is true when the feature is present and is not `false`, `0` or `""`.
- `get_feature(claims, key)` returns the raw value as `Option<&FeatureValue>`.

## Where entitlements are read

| Where | How |
| --- | --- |
| Server, from the session | `session.claims`, from `handlers.get_session(&request)` or the `AuthSession` extractor. Claims are renewed every `claims_renew_seconds`. |
| Browser | `GET /auth/me` returns the user as a `SessionUser` in camelCase JSON, with `roles`, `permissions`, `features` normalised to empty values and `plan` and `orgId` when present. |
| Bearer-protected API | `verified.claims` of `BearerVerifier::new(auth, audience)?.verify(token).await?`. |

::callout{icon="i-lucide-triangle-alert" color="warning"}
Checks in the browser improve the interface; they are not a security boundary. Enforce every entitlement on the server, in the route that does the work.
::

`SessionUser` never carries tokens, `sid` or timestamps: those stay on the server. `to_session_user(&claims)` builds it from an `IdTokenClaims`, and `user.to_json()` gives the camelCase JSON value (`emailVerified`, `orgId`) without the empty optional members.
