The crate is published to crates.io as `auth-ai` under the **MIT** license, and imported as `auth_ai`. It requires Rust 1.89 or later (edition 2024).

## Channels

| Channel | Trigger | crates.io version | Install |
| --- | --- | --- | --- |
| Stable | Creating a GitHub release `vX.Y.Z` from `main`. | `X.Y.Z` | `cargo add auth-ai` |
| Pre-release | Creating a GitHub release marked _pre-release_ for a version such as `X.Y.Z-rc.N`. | `X.Y.Z-rc.N` | `cargo add auth-ai@=X.Y.Z-rc.N` |
| Nightly | A manual run of the **Nightly** workflow, from `develop` or `main`. | `X.Y.Z-dev.YYYYMMDDHHMM` | `cargo add auth-ai@=X.Y.Z-dev.YYYYMMDDHHMM` |

Cargo never selects a SemVer pre-release for a requirement such as `0.1`: you must name the exact pre-release version (`auth-ai = "=X.Y.Z-dev.YYYYMMDDHHMM"` in `Cargo.toml`).

### Stable

The release is the trigger: create the GitHub release (and its tag `vX.Y.Z`) from `main` once the version is set in `Cargo.toml`. The workflow never creates a release or a tag itself. It:

1. runs the same quality gates as continuous integration (format check, Clippy with warnings denied, unit, integration and doc tests, documentation built with warnings denied, a build of the package that is published, and an advisory audit of the dependencies);
2. requires that the tag matches the version in `Cargo.toml`, that the pre-release flag of the release matches the version (a SemVer suffix such as `-rc.1` or `-dev.…` means pre-release), and that a stable release points at a commit on `main`;
3. publishes the crate with `cargo publish --locked`.

If a run fails, fix the cause, then delete the release **and** its tag and create them again. crates.io never accepts the same version twice: bump the version if one was already uploaded.

### Nightly

A nightly is published as a SemVer pre-release `X.Y.Z-dev.YYYYMMDDHHMM`, where the suffix is the UTC date and minute of the run. `X.Y.Z` is the version in `Cargo.toml`, or the next patch when that version is already on crates.io, so a nightly never sorts before a stable release. The version exists only in the workflow's workspace: no commit is made, so no version bump lands on the branch. The nightly runs the same quality gates first.

Use a nightly to try an unreleased change. Nothing about its API is guaranteed. Nightlies stay on crates.io: a maintainer can yank one, but it is never deleted.

### Authentication to crates.io

Both workflows publish through [crates.io Trusted Publishing](https://crates.io/docs/trusted-publishing) (OpenID Connect): no registry token is stored in the repository. Each workflow file (`release.yml`, `nightly.yml`) must be registered as a trusted publisher of the `auth-ai` crate on crates.io (owner `circle-rd`, repository `auth-ai-rs`, GitHub environment `crates-io`). A trusted publisher is configured on an existing crate, so a maintainer uploads the very first version by hand with `cargo publish`.

## Versioning

The project follows Semantic Versioning. While the major version is `0`, a breaking change bumps the **minor** version. A breaking change is anything that alters the public contract: a changed signature or default, a removed export, a changed error code or response shape, or a raised minimum Rust or dependency version, the minimum supported Rust version included. Breaking changes are listed in the [changelog](https://github.com/circle-rd/auth-ai-rs/blob/main/CHANGELOG.md), with a migration note, and the old behaviour is removed rather than kept behind a compatibility shim.

## Supported toolchains and dependencies

Continuous integration runs the checks on Rust 1.89.0 (the minimum supported version, pinned in `rust-toolchain.toml`) and on stable. The runtime dependencies are `reqwest` (`0.13`, with rustls), `aws-lc-rs` (`1.19`), `serde`, `serde_json`, `tokio` (`1.54`), `url`, `thiserror`, `zeroize`, `async-trait`, `base64`, `time` and `percent-encoding`; `axum` (`0.8`) is optional, behind the `axum` feature.
