---
title: Resource sharing
description: Ask auth-service whether a user may use a shared resource, list what they can reach, report the validation or loss of ownership of a resource you own, and report what a provider billed.
---

auth-service lets a user or an application **own** a resource (a model, an agent, an MCP server, an SSH account, or a resource of a scheme your application defines) and **share** it with users, organisations, plans, other applications or every member of the application. The decision is always auth-service's: your code asks and obeys. Concepts and operator side: [Resource sharing](https://docs.circle-cyber.com/auth-service/docs/project/resource-sharing-final-design) in the auth-service documentation.

The machine calls below are the `machine.resources` client of the [machine API](/docs/reference/server-api); the self-service calls are `user.resources` on a `UserAi`.

## Prerequisites

- auth-service runs with `RESOURCE_SHARING_ENABLED` on, and sharing is enabled for the application that offers the resource. Without it the routes do not exist and every call returns `API_001` with the `status` detail `404`.
- A **confidential** application, as for the rest of the machine API.
- The machine scope of what you call:

| You are | Scope | Calls |
| --- | --- | --- |
| The validator bound to a resource scheme (your application owns the scheme) | `resources:validate`, given to new confidential applications | `validate`, `invalidate` |
| An enforcement point that admits users to resources | `resources:authorize`, granted by a superadmin | `authorize`, `list_accessible` |
| A metering component that reports what a provider billed | `resources:usage:write`, granted to the platform's metering components only | `record_usage` |
| The application acting for a signed-in user on their own resources | `resources:self:manage`, added by `resource_sharing(true)` at sign-in | `user.resources` |

Every decision is taken for the **application whose credential you use**: it sees the resources that application owns and the ones shared with it, never everything a user owns. A missing scope makes the call return `TOK_004` with the scope in the `scope` detail. The self-service client is different: it uses the signed-in user's token, so it needs no client secret; a user token is confined to its client's application, so `user.resources` sees that application's resources only.

## Admit a user to a resource

```rust
use auth_ai::AuthAiError;
use auth_ai::server::{
    Allowed, AuthorizeDecision, AuthorizeRequest, BearerVerifier, EventSource, MachineApi,
    ResourcePermission,
};

async fn admit(
    machine: &MachineApi,
    verifier: &BearerVerifier,
    authorization: Option<&str>,
    request_id: &str,
) -> Result<Option<Allowed>, AuthAiError> {
    let token = verifier.verify_header(authorization).await?;
    let Some(user_id) = token.user_id.as_deref() else {
        return Ok(None); // a user token is required
    };

    let request = AuthorizeRequest {
        subject_id: user_id, // the verified `sub`
        actor_client_id: Some(&token.client_id), // the verified `azp`, kept for audit
        resource_uri: "gine://project-42",
        audience: "https://api.example.com",
        permission: Some(ResourcePermission::Write), // `read` by default
        request_id: Some(request_id),
        source: Some(EventSource::External),
    };
    // Fail closed: only an `Allowed` answer admits, and an error is a refusal too.
    Ok(match machine.resources.authorize(&request).await {
        Ok(AuthorizeDecision::Allowed(allowed)) => Some(allowed), // allowed.access_kind, allowed.permission
        Ok(AuthorizeDecision::Denied) => None,
        Err(err) => {
            tracing::warn!(error = %err.to_json(), "authorize failed");
            None
        }
    })
}
```

- **Take `subject_id` and `audience` from a token you verified**, never from a request body: auth-service trusts them as they come. `actor_client_id` only labels the access log; the calling application is your machine credential, so there is no `client_id`.
- **Fail closed.** Only an `AuthorizeDecision::Allowed` answer is an admission (`decision.allowed()` gives the `Option<&Allowed>`). A denial carries no reason, so it cannot be used to probe which resources exist, and an `authorize` that returns an error (`API_001`, `API_002`, a timeout) is a denial too. An answer this SDK does not know fails to parse as `API_002`: it can never read as an admission.
- **`Write` covers `Read`.** Ask for the level the request needs: a `Read` grant is refused when you ask for `Write`. The answer carries the level the user holds (`allowed.permission`), so an interface can show or hide actions without trying them. `allowed.owner_id` is `Some` only when your application owns the resource.
- Ask for every request that needs it: the answer reflects revocations, bans and membership changes at once, so do not keep it longer than the request.
- `request_id` and `source` are optional: they correlate the access event with your own request id and name the enforcement point in the access log (`EventSource::Gateway` by default).

## List what a user can reach

```rust
use auth_ai::AuthAiError;
use auth_ai::server::MachineApi;

async fn list(machine: &MachineApi) -> Result<(), AuthAiError> {
    for resource in machine
        .resources
        .list_accessible("user-sub", Some("llm"))
        .await?
    {
        println!(
            "{} {:?} {:?}",
            resource.resource_uri, resource.access_kind, resource.permission
        );
    }
    Ok(())
}
```

The list holds what your application owns and what was shared with it. Use it to filter what you show, and call `authorize` for the decision itself. Pass `None` instead of a scheme to list every scheme.

## Validate a resource you own

When an owner asks to validate a resource of a scheme your application defines, auth-service marks it pending and waits for your answer. You prove the ownership your own way (the project belongs to the caller, the object exists), then report:

```rust
use auth_ai::AuthAiError;
use auth_ai::server::{MachineApi, ValidationResult};
use serde_json::{Map, json};

async fn validate(machine: &MachineApi, resource_id: &str) -> Result<(), AuthAiError> {
    let mut evidence = Map::new();
    evidence.insert("checkedBy".to_owned(), json!("my-app"));
    machine
        .resources
        .validate(
            resource_id,
            ValidationResult::Validated,
            None,
            Some(&evidence),
        )
        .await?;

    machine
        .resources
        .validate(
            resource_id,
            ValidationResult::ValidationFailed,
            Some("This project belongs to another account"),
            None,
        )
        .await?;
    Ok(())
}
```

`reason` (500 characters at most) is shown to the owner. `evidence` is stored with the resource: never put a secret in it. Both calls return the `ResourceState` as auth-service now holds it, with its `status`.

When ownership is lost later (the project was deleted, a host key changed), disable the resource so access stops at once:

```rust
use auth_ai::AuthAiError;
use auth_ai::server::MachineApi;

async fn invalidate(machine: &MachineApi, resource_id: &str) -> Result<(), AuthAiError> {
    machine
        .resources
        .invalidate(resource_id, "project-deleted")
        .await?;
    Ok(())
}
```

Only the client bound to the resource's scheme may call `validate` and `invalidate`; another client gets `API_001` with the `apiCode` detail `AUTH_011`.

## Share from the signed-in user

An application acting for a signed-in user declares and shares that user's own resources. Set `resource_sharing(true)` on the configuration so sign-in asks for `resources:self:manage` and the auth-service audience; the client is then `ai.for_user(sub)?.resources`.

```rust
use auth_ai::{AuthAiError, CreateResource, ResourceAudience, UserAi};

async fn declare(user: &UserAi, application_id: &str) -> Result<(), AuthAiError> {
    let resource = user
        .resources
        .create(&CreateResource {
            application_id,
            scheme: "gine",
            display_name: "Firmware",
            locator: Some("job-1"),
            metadata: None,
            // Share it in the same call: a refused audience leaves no resource behind.
            audience: Some(&ResourceAudience::organization("org-1")),
        })
        .await?;
    println!("{} {}", resource.id, resource.status); // pending_validation
    Ok(())
}
```

| Goal | Calls |
| --- | --- |
| Find where the user may create | `list_member_applications` (`can_create`), `list_organizations` |
| Manage their resources | `list_owned`, `get_resource`, `create`, `update`, `delete`, `request_validation` |
| Share them | `list_grants`, `create_grant`, `update_grant`, `revoke_grant`, `delete_grant`, `share_with_application` |
| Read what they may use | `list_accessible`, `get_catalogue` |

A `create_grant` subject is a `User` (`subject_id` or `subject_email`, never both; auth-service resolves the e-mail among active members and gives the same answer for an unknown address and a non-member), an `Organization` (the owner must belong to it), a `Plan`, `Everyone` or an `Application`, whose `subject_id` is the application slug. `permission` is `Read` (the default) or `Write`, which also covers `Read`; it is left out of the request when `None`. `expires_at` must be in the future. Every id must be a UUID, and an empty update or an invalid audience returns `CFG_001` before any request.

```rust
use auth_ai::{AuthAiError, ResourcePermission, ShareWithApplication, UserAi};

async fn share(user: &UserAi, resource_id: &str, grant_id: &str) -> Result<(), AuthAiError> {
    // Raise a grant to `Write` without revoking it: RES_014 when the scheme only supports `Read`,
    // RES_015 for an inactive grant.
    user.resources
        .update_grant(resource_id, grant_id, ResourcePermission::Write)
        .await?;

    // Revoke an active grant, then delete the revoked row for good (RES_020 while it is active).
    user.resources.revoke_grant(resource_id, grant_id).await?;
    user.resources.delete_grant(resource_id, grant_id).await?;

    // Share up to 100 resources with one application; each entry reports its own outcome.
    let results = user
        .resources
        .share_with_application(
            &[resource_id],
            &ShareWithApplication {
                application_slug: "chat",
                permission: Some(ResourcePermission::Read),
                expires_at: None,
            },
        )
        .await?;
    for result in results {
        println!("{} {:?} {:?}", result.resource_id, result.grant_id, result.code);
    }
    Ok(())
}
```

`delete` removes a resource for good, with its grants, and returns the `Resource`; auth-service refuses it with `RES_019` while the relay still serves the model. `delete_grant` accepts only a grant that is already revoked or expired. A `Resource` read on its own carries `permissions`, the levels its scheme supports. `list_accessible` returns what the user may use through the calling application, each with its `permission`.

## Receive resource webhooks

When the application registers a `resourceWebhookUrl`, auth-service delivers `resource.grant.created`, `resource.grant.revoked`, `resource.grant.updated` (a level change) and `resource.deleted` to it. Verify each delivery with `auth_ai::server::verify_resource_event`: it checks the `X-Auth-Service-Signature` HMAC over `<timestamp>.<raw body>`, bounds the timestamp (300 seconds by default) and parses a typed `ResourceEvent`, an enum with one variant per event.

```rust
use auth_ai::AuthAiError;
use auth_ai::server::{ResourceEvent, ResourceWebhookVerifier};

fn handle(
    verifier: &ResourceWebhookVerifier,
    headers: &[(String, String)],
    body: &[u8],
) -> Result<(), AuthAiError> {
    match verifier.verify(headers, body)? {
        ResourceEvent::GrantCreated(event) | ResourceEvent::GrantUpdated(event) => {
            /* sync event.grant for event.recipients */
        }
        ResourceEvent::GrantRevoked(event) => { /* revoke local access */ }
        ResourceEvent::Deleted(event) => { /* drop event.resource.id */ }
    }
    Ok(())
}
```

Grant events carry `resource` (with `status`), `grant` (`permission`, and `previous_permission` on an update) and `recipients`. `resource.deleted` carries the resource only, with no grant and no recipients. `owner_id` reaches only the application that owns the resource. Delivery is at least once: deduplicate on `ResourceEvent::event_id()`. `recipients.user_ids` is `None` with `all_members: true` when the grant reaches the whole application. Use `ResourceWebhookVerifier::new(secret).tolerance_seconds(..)` to change the window. A missing or malformed header, a stale timestamp, a wrong signature or an unexpected body (a grant event without a `permission`, an unknown event type) returns `REQ_001`.

## Report the usage of a resource

A metering component reports what a provider billed for a resource. auth-service owns accounting; this is the only write and reading stays with it. It needs the scope `resources:usage:write`, which is granted to the platform's metering components only, never to an application by default.

```rust
use std::time::SystemTime;

use auth_ai::AuthAiError;
use auth_ai::server::{MachineApi, UsageRecord, UsageSource};

async fn report_usage(
    machine: &MachineApi,
    decision_id: &str,
    started_at: SystemTime,
    resource_id: &str,
    event_id: &str,
) -> Result<(), AuthAiError> {
    let receipt = machine
        .resources
        .record_usage(&UsageRecord {
            decision_id, // from the `authorize` that admitted the request
            started_at,  // when that request started
            resource_id,
            resource_uri: "llm://acme/gpt-x",
            request_id: event_id, // 64 lowercase hex characters, stable per event
            occurred_at: SystemTime::now(),
            source: UsageSource::Provider,
            cost_usd: Some("0.0042"),
            prompt_tokens: Some(120),
            completion_tokens: Some(30),
            total_tokens: Some(150),
        })
        .await?;
    println!("{} {}", receipt.usage.id, receipt.replayed);
    Ok(())
}
```

- **Bound to the admission.** `decision_id` (`Allowed::decision_id`) names the person and the application, so a usage event cannot claim another one. It is short-lived and only the client that obtained it may present it; `started_at` must fall within its lifetime (`Allowed::expires_at`).
- **Idempotent.** `request_id` is the event's trusted identifier: 64 lowercase hexadecimal characters, stable per event. Replaying the same event is safe: the `UsageReceipt` carries the stored `usage` and `replayed: true`.
- **Time window.** `occurred_at` is a `SystemTime`, at most 5 minutes ahead and at most 30 days back.
- **Cost.** `UsageSource::Provider` requires `cost_usd`, a plain decimal string such as `"0.0042"` (no sign, no exponent). The token counts are optional.
- **No figures.** Use `UsageSource::Unsupported` when the provider reports nothing, and set `cost_usd` and the three token counts to `None`: an unsupported event must carry neither.
- **Refusals.** A payload that conflicts with the stored event for the same `request_id` is refused with `RES_012`, a caller with no access to the resource with `RES_011`, and a decision that is expired, forged or issued to another client with `RES_016`. All come back as `API_001`, with the code in the `apiCode` detail.
- An invalid record (an empty `decision_id`, an id that is not a UUID, a `request_id` that is not 64 lowercase hex characters, an `occurred_at` outside the window, a missing cost for `Provider`) returns `CFG_001` before any request.

## Errors

| Situation | Error |
| --- | --- |
| Invalid input (id not a UUID, empty subject, reason too long, bad usage record, bad share) | `CFG_001`, before any request |
| Scope not granted | `TOK_004`, `scope` detail |
| auth-service refused (`AUTH_011`, `RES_001`, `RES_004`, `RES_011`, `RES_012`, `RES_014`, `RES_015`, `RES_016`, `RES_019`, `RES_020`…) | `API_001`, `status` and `apiCode` details |
| Unexpected answer | `API_002` |
